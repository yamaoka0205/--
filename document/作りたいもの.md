## 1. 企画概要

予約管理システムをまだ導入していない小規模飲食店向けに、**AI電話受付と予約管理を一体化した、複数店舗対応のクラウドサービス（SaaS）**を開発する。

主な対象は、電話で予約を受け付け、紙の予約台帳やExcel・Googleスプレッドシートなどで管理している店舗。既存の予約管理システムを前提にせず、電話受付から空席確認、予約確定、予約台帳への登録までを1つのサービス内で完結させる。

顧客からの電話をAIが受け、店舗情報への質問に回答する。予約希望の場合は、日時・人数・名前・電話番号などを聞き取り、店舗がAI予約用に開放した席と予約時間を照合する。条件を満たす場合は予約を登録し、管理画面に反映する。

店舗は管理画面から営業時間、FAQ、席構成、AI予約に使う席数、標準利用時間、予約状況などを管理できる。複数の店舗が同じシステム基盤を利用するが、店舗ごとの設定・予約・通話履歴は分離する。

### 解決したい課題

- 接客・調理中に電話へ出られず、予約や問い合わせを取りこぼす。
- 電話で受けた予約を紙や表計算ソフトへ転記する手間がある。
- 予約時間や人数の聞き間違い、記入漏れが発生する可能性がある。
- 予約客だけで席を埋めると、予約なしで来店する客の席が不足する。
- 予約管理システム未導入の店舗では、AI電話だけを導入しても予約を記録・管理する仕組みが別途必要になる。
- 電話AIと予約台帳が別サービスの場合、契約・設定・管理先が分かれ、情報の二重管理が発生する可能性がある。

本作品では、**予約管理システムを持たない店舗が、電話受付と予約管理を別々に導入せず、最初から一体の仕組みとして利用できること**を中心価値とする。

ただし、AI電話と自社予約台帳を一体提供する競合（GATEなど）はすでに存在するため、「一体化」だけを独自性とはしない。導入対象を初めて予約管理をデジタル化する小規模店に絞り、導入・設定・日常操作の簡単さを差別化仮説として検証する。

## 2. 想定ターゲット

### 主な対象

- 個人経営、または小規模チェーンの飲食店
- 電話予約を受け付けている店舗
- **予約管理システムをまだ導入していない店舗**
- 紙の予約台帳やExcel・Googleスプレッドシートで予約を管理している店舗
- 少人数で接客・調理・電話対応を兼任している店舗
- 既存システムの高度な機能や外部連携までは必要としていない店舗
- まずは電話予約と基本的な予約台帳を簡単にデジタル化したい店舗

### 対象外になりやすい店舗

- 予約をほとんど受け付けていない店舗
- 来店順で案内することが中心で、席予約を管理しない店舗
- 既存の予約台帳や複数の予約経路を高度に統合する必要がある店舗（初期版では外部連携を想定しない）
- 大規模チェーンで本部一括管理、複雑な配席、複数媒体・POS・CRM連携が必須の店舗

### 利用者

1. **店舗管理者**：店舗情報、席構成、AI予約枠、FAQ、予約を管理する。
2. **電話をかける顧客**：店舗への質問や予約を電話で行う。
3. **サービス運営者**：店舗アカウントや利用状況を管理する。

## 3. サービスの基本機能

### 3.1 店舗登録・ログイン

- **初期（就職作品・MVP）**：運営者（自分）がデモ用店舗を登録する。
- **完成系**：店舗が自分でアカウントを作成し、利用申し込みできる（セルフサインアップ）。**利用開始には運営者の承認を必須とする。**
- 店舗名、住所、電話番号、営業時間などを登録する。
- 店舗ごとに管理画面へログインできる。
- 店舗ごとのデータを分離する。

※完成系のセルフ申し込みは差別化仮説（初めて導入する店が自分で始められること）と直結する。初期版ではデモ登録で電話→予約の核を先に通し、セルフ申し込み＋運営者承認は後段で実装する。

### 3.2 AI電話受付

- Amazon Connectで着信を受ける。
- **開発・就職作品デモの主経路は Connect の WebRTC（localhost）**とする。実電話番号での着信は、取得できた場合の追加デモとする。
- 店舗ごとに着信先の識別子を1つ持ち（全店で重複不可）、着信先から対象店舗を特定する。WebRTC では通話開始時に店舗識別子を渡す。
- 人間へ引き継ぐ転送先も店舗ごとに1つ。デモ店には開発者の番号を入れる。
- 通話履歴には、かけてきた番号と着信先番号を保存する。
- 店舗の営業時間、住所、FAQ、サービス情報などを取得する。
- AIが店舗情報に基づいて回答する。
- AIが回答できない、または情報に確信を持てない場合は、推測で答えず人間へ引き継ぐ。
- 人間への引き継ぎは **Amazon Connect の外部転送** で、デモでは開発者自身の電話へ飛ばす。

### 3.3 AI電話予約

AIは顧客との会話から、少なくとも次の情報を聞き取る。

- 予約希望日
- 予約希望時刻
- 人数
- 予約者名
- 折り返し可能な電話番号（必要な場合）

聞き取った内容を顧客に読み上げて確認し、予約条件を満たす場合に確定する。

### 3.4 席の設定とAI予約枠

店舗は初期設定時に、**卓単位**で席構成を登録し、そのうちAIが予約に使ってよい卓を設定する（例：「4人用テーブル3つ」「6人用テーブル2つ」）。席数だけの管理にはしない。

**設定例（AI予約に開放する卓）**

| テーブル種別 | AI予約に開放する数 |
|---|---:|
| 4人用テーブル | 4卓 |
| 6人用テーブル | 2卓 |
| 合計 | 6卓 |

店舗にこれ以外の卓がある場合、その卓は予約なしの来店客向けに残す。AIは設定されたAI予約枠の外にある卓を勝手に予約しない。

人数とテーブルの対応は、次の暫定ルールとする（実装前に必要なら修正する）。

| 人数 | 使用テーブル | 備考 |
|---|---|---|
| 1〜4人 | 4人用 | 小さめ人数も4人卓を使う |
| 5〜6人 | 6人用 | |
| 7人以上 | なし | AIだけで確定せず、人間へ引き継ぐ |

複数卓を組み合わせる扱いは初期版の対象外とする。

### 3.5 予約時間・重複判定

- **店舗が初期設定で標準利用時間を決める。デモ店舗の初期値は120分。**
  - 目安の根拠：ディナー滞在はおおむね90〜120分、予約システムでもレストラン／居酒屋ディナーは120分前後が一般的。ぐるなび調査では日本人客のディナー平均約133分。初期版は店舗ごとに1つの値だけを持つ。
- 利用時間はAIが推測して決めるものではなく、顧客が毎回指定するものでもない。
- 予約開始時刻の刻みは **15分**。
- 最終受付は、営業終了から標準利用時間を引いた時刻まで。
- 予約開始時刻と店舗が設定した利用時間から終了時刻を計算する。
- 例：標準利用時間が120分の場合、18:00開始の予約は20:00終了、19:00開始の予約は21:00終了として空席判定する。
- 既存予約と時間が重なるAI予約用テーブルは使用できない。
- 利用時間が終了した後の時間帯では、同じテーブルを再び予約候補にできる。
- 予約の確認から確定までの間に別の予約が入る可能性があるため、確定時に空席を再確認し、二重予約を防止する。
- AI予約枠が埋まっている場合は、別時間を提案するか、外部転送で人間へ引き継ぐ。
- 予約変更・キャンセルは初期版では後回し。

**重要：** 「6卓をAI予約に開放する」は、店舗全体の全席を予約で埋めてよいという意味ではない。AI用に設定した卓だけを使用し、その他の卓は当日来店客用として残す。

### 3.6 予約管理画面

店舗管理者は次の情報を確認・操作できる。

- 日付・時間ごとの予約一覧
- 予約者名、人数、電話番号
- 使用テーブル
- 予約の状態（確定、変更、キャンセル等）
- 店舗の席構成とAI予約枠
- 標準利用時間
- 店員による手動予約登録
- AI電話の通話履歴・対応結果

### 3.7 問い合わせ・通話履歴

- 問い合わせ日時
- 通話内容の文字起こし
- AIによる要約
- AIが回答したか、人間へ引き継いだか
- 対応状況（未対応、対応中、対応済み等）

営業時間外の電話は、要件を聞き取って記録し、後から店舗が確認できるようにする。営業時間開始時の自動通知は追加候補とする。

### 3.8 利用量記録

将来的な料金管理に備え、通話単位の利用量を記録する。

- 店舗ID、通話ID
- 通話開始・終了時刻、通話秒数
- 着信・発信の区分
- 転送の有無・転送時間
- AIモデルの入出力トークン数（取得できる場合）
- 音声認識・音声合成等の利用量（取得できる場合）

月次集計・概算料金表示は追加候補。実際のAWS請求額と完全一致するとは限らないため、表示する場合は「概算」とする。

## 4. 複数店舗対応（マルチテナント）

**最終的には複数店舗対応を目指す。** データモデルには最初から店舗ID（tenantId）を持たせ、開発初期は店舗1件で電話→予約確定の流れを完成させる。その後、店舗追加と認証・運用面を拡張する。

### 店舗ごとに分離するデータ

- 店舗情報・営業時間
- FAQ・AI回答設定
- 電話番号（またはデモ用識別子）との紐付け
- 席構成・AI予約枠・標準利用時間
- 予約情報
- 通話履歴・文字起こし・要約
- 利用量

### 必須のセキュリティ要件

- すべての店舗データに店舗ID（tenantId）を関連付ける。
- ログインユーザーが所属する店舗のデータだけを参照・更新できるようにする。
- 電話番号／デモ用識別子から店舗を特定した後は、その店舗の情報だけをAIに渡す。
- A店の管理画面からB店の予約・通話履歴を閲覧できないようにする。
- サーバー側でも権限と店舗IDを検証する。画面上で隠すだけの制御にしない。

### 電話着信時の流れ

1. 顧客が店舗へ発信する（デモでは localhost の WebRTC から開始してもよい）。
2. Amazon Connectが着信を受ける。
3. 着信先番号（またはデモ用の店舗識別子）を取得する。
4. Lambdaが電話番号／識別子と店舗IDの対応を検索する。
5. 対象店舗の営業時間・FAQ・予約設定を取得する。
6. AIが応答・予約受付を行う。予約判定・登録は共通APIを呼び出す。
7. 通話・予約データを対象店舗IDと紐付けて保存する。

## 5. 技術構成案（AWS中心）

### 予約API・DBの基本構成（採用方針）

| 技術 | 想定する役割 |
|---|---|
| Amazon API Gateway | HTTPリクエストを受け付け、Lambdaへ渡す |
| AWS Lambda（Python） | 予約登録、空席確認、予約変更、キャンセル、入力検証など |
| Python標準機能 | Lambdaの処理を実装。FastAPI・FlaskなどのWebフレームワークは初期構成では使用しない |
| boto3 | PythonからDynamoDBなどのAWSサービスを操作するAWS SDK |
| Amazon DynamoDB | 店舗、席、予約、FAQ、通話履歴、利用量を保存 |
| React + TypeScript | 予約一覧、予約登録、店舗設定などの管理画面（電話経路のあとに本格実装） |

開発順は **予約判定API → Connect WebRTC電話 → 管理画面** とする。LambdaはHTTPサーバーとして常時起動するのではなく、API GatewayやConnectから呼び出されたときに処理を実行する。

処理経路は次の2系統。

1. **電話経路（先に通す）**：Connect（WebRTC）→ Lambda → 予約判定・登録API → DynamoDB
2. **管理画面経路（後から載せる）**：React → API Gateway → Python Lambda → DynamoDB

予約処理は電話AIと管理画面で共通利用する。

### 電話AI・認証・補助機能の構成候補

| 技術 | 想定する役割 |
|---|---|
| Amazon Connect | 着信、通話フロー、転送、**WebRTC（localhost検証・発表デモの主経路）** |
| Amazon Lex | 音声認識・会話フロー（採用範囲は要検討） |
| Amazon Bedrock | FAQ回答、自然言語理解の補助、要約 |
| Amazon Cognito | 店舗ユーザーの認証 |
| Amazon S3 | 音声データ等を保存する場合に利用 |
| Amazon EventBridge | 定期処理や通知を追加する場合に利用 |

※React・TypeScript・API Gateway・Python Lambda・DynamoDBを基本構成とする。Connect・Lex・Bedrockの役割分担、音声の入出力方式、料金、リージョンは検証して確定する。実電話番号の取得は必須にしない。Lambdaの予約確定処理では、同時予約による二重確保を防ぐため、DynamoDBの条件付き書き込みやトランザクション等を設計する。

### 予約データ設計で重視すること

- 店舗IDと予約IDを紐付ける。
- 予約開始・終了時刻、人数、使用テーブル、状態を記録する。
- 予約確定処理で同じ席・同じ時間帯を二重に確保できないようにする。
- 予約変更・キャンセル時に席の空き状況が正しく更新されるようにする。
- 複数の電話が同時に来ても予約枠が壊れないよう、DB側で排他・条件付き更新等を設計する。

AWSのサービス数を増やすこと自体ではなく、**電話・予約・データ分離・同時実行という課題をどう設計して解決したか**を説明できることを重視する。

## 8. 企画説明文（仮）

予約管理システムをまだ導入していない小規模飲食店向けに、AI電話受付と予約管理を一体化した複数店舗対応SaaSを開発する。紙やExcelなどで予約を管理している店舗が、初めて予約管理をデジタル化する際に、導入・設定・日常操作が簡単な一体型サービスを選べることを目指す（「一体型であること」自体はGATE等にもあるため、独自性の主張は簡単さの検証に置く）。顧客からの電話（デモではConnect WebRTC可）にAIが応答し、店舗情報に関する質問への回答や予約受付を行う。予約時には、店舗がAI予約用に設定したテーブルと、店舗が初期設定した標準利用時間を照合し、空席がある場合のみ予約を確定する。AI予約用の席以外は予約なしの来店客向けに残すことができる。店舗は管理画面から予約・席構成・通話履歴を管理でき、複数店舗が同じ基盤を利用しながらデータを安全に分離する。AWSを活用し、電話受付から予約登録・管理までの業務を自動化することを目指す。

## 9. 決定事項・未決定事項

### 決定した方針

- 人数とテーブルの割り当て：1〜4人→4人用、5〜6人→6人用、7人以上→人間引き継ぎ
- 席設定は卓単位（例：4人用テーブル3つ）
- 標準利用時間の初期値：120分（ディナー相場・予約システム目安に基づく）
- 予約開始時刻の刻み：15分
- 最終受付：営業終了から標準利用時間を引いた時刻まで
- 人間引き継ぎ：Connectの外部転送で自分の電話へ
- 予約変更・キャンセル：初期版では後回し
- 電話デモの主経路：Connect WebRTC（localhost）。実電話番号は任意
- 開発順：予約判定API → WebRTC電話 → 管理画面
- マルチテナント：tenantIdは最初から持ち、初期は1店舗運用
- 店舗登録：初期は運営者がデモ店舗を登録。**完成系は店舗が自分でアカウント作成・申し込み → 運営者承認必須**
- 複数卓の結合配席：初期版対象外

### まだ決める必要があるもの

- 正式な作品名
- 予約確定時の本人確認・電話番号確認の要否
- 予約通知（SMS等）の採否
