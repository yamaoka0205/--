# 作る道筋（開発計画）
## 予約管理システム未導入の小規模飲食店向け AI電話受付・予約管理SaaS

- 制作形態：個人制作
- 目標：就職作品イベントで、企業の技術者に電話デモ（WebRTC可）と管理画面を見せ、設計意図を説明できる状態にする。
- 方針：**予約判定APIを先に固め、Connect WebRTCで電話→予約確定を通し、その後に管理画面を載せる。tenantIdは最初から持つが、動かす店舗はまず1件。**
- ターゲット：予約管理システムをまだ導入しておらず、紙・Excel等で予約を管理している小規模飲食店。
- 電話デモ：実電話番号の取得を必須にしない。開発・発表は **Amazon Connect の WebRTC（localhost）** で着信・会話を再現する。実番号が取れれば追加デモとする。

### 採用する基本技術構成

- フロントエンド：React ＋ TypeScript（管理画面は電話一本通したあとに本格実装）
- API受付：Amazon API Gateway
- バックエンド：AWS Lambda（素のPython）
- データベース：Amazon DynamoDB
- PythonからAWSサービスを操作：boto3
- 電話：Amazon Connect（WebRTCでローカル検証）
- 会話AI：Amazon Lex（音声認識・会話のターン管理）＋ Amazon Bedrock（発話から項目を取り出す・FAQ回答）。分担は Phase 2 の表のとおり
- 初期構成ではFastAPI・FlaskなどのWebフレームワークは使用せず、API GatewayからLambdaのハンドラーを直接呼び出す。
- 電話AIからの予約操作と、後から作る管理画面からの予約操作は、**同じ予約判定・登録API**を利用する。

基本的な処理経路は次の2系統。

1. **電話経路（先に完成させる）**：Connect（WebRTC）→ Lambda → 予約判定・登録API → DynamoDB
2. **管理画面経路（後から載せる）**：React → API Gateway → Python Lambda → DynamoDB

---

## 1. 完成目標（MVP）

最初の完成ラインは、次の一連の流れが実際に動くこと。

1. 店舗データ（tenantId付き）・営業時間・席構成・AI予約枠・標準利用時間が登録されている。
2. 開発者が localhost の Connect WebRTC から店舗向けの通話を開始できる。
3. AI（または会話フロー）が予約希望日時・人数・名前などを聞き取る。
4. 予約判定APIが店舗設定の利用時間で終了時刻を計算し、AI予約枠の空席を確認する。
5. 予約可能なら内容を復唱して確定する。
6. 予約情報がDBへ登録される。
7. 管理画面（後段で実装）にその予約が表示される。
8. データは tenantId で分離され、別店舗アカウントではその予約を閲覧できない。

この流れを最優先にし、Webサイト差分検出や高度な料金計算などは後回しにする。

**やらないこと（初期の誤解を防ぐ）**

- 管理画面を厚く作ってから電話に入る順序にはしない。
- 電話会話だけ先に作り、予約判定を後付けする順序にもしない。
- 「1店舗完成後に tenantId を足す」方式にはしない。最初から tenantId を持ち、店舗数は1件で運用する。

## 2. 開発フェーズ

### Phase 0：要件を確定する（実装ブロッカーを閉じる）

実装前に、予約ルールとデモ方式を具体化する。未決のまま Phase 1 に入らない。

**予約ルール（決定）**

- 席の設定単位は **卓単位**（例：「4人用テーブル3つ」「6人用テーブル2つ」）。席数だけの管理にはしない。
- AI予約に開放するテーブル数、当日来店客用に残すテーブル数は店舗設定で決める。
- **人数割り当て**

| 人数 | 使用テーブル | 備考 |
|---|---|---|
| 1〜4人 | 4人用 | 小さめ人数も4人卓を使う |
| 5〜6人 | 6人用 | |
| 7人以上 | なし | 人間へ引き継ぎ（外部転送） |

- **標準利用時間の初期値：120分**
  - 根拠：飲食店のディナー滞在はおおむね90〜120分、予約システムでもレストラン／居酒屋ディナーは120分前後が目安とされる。ぐるなび調査では日本人客のディナー平均約133分。初期版は店舗ごとに1つの標準利用時間だけを持ち、デモ店舗の初期値を120分とする。ランチ／ディナー別・曜日別は将来拡張。
  - AIが利用時間を推測しない。顧客が毎回指定もしない。店舗設定値のみ使う。
  - 例：120分なら18:00開始→20:00終了、19:00開始→21:00終了。
- 予約開始時刻の刻み：**15分**
- 最終受付時刻：営業終了時刻から標準利用時間を引いた時刻まで（例：22:00閉店・120分なら最終開始20:00）。
- 営業時間は同じ日の中で完結する店舗だけを扱う。日付をまたぐ営業（例：17:00〜翌1:00）は初期版の対象外。
- 予約変更・キャンセル：**初期版では後回し**（手動の状態変更が必要になったら最小限で足す）。
- AIが確定できない場合：**Amazon Connect の外部転送で、開発者自身の電話へ飛ばす**。
  - 外部転送には、発信者番号として使う Connect 側の取得済み番号が1つ必要（WebRTC の通話を転送する場合も同じ）。
  - 番号を取得できない場合は、ブラウザのエージェント画面（CCP）へ転送し、開発者が店舗スタッフ役として応答する。

**現時点の席設定例（AI予約に開放する卓）**

| 種類 | AI予約に開放する数 |
|---|---:|
| 4人用 | 4卓 |
| 6人用 | 2卓 |
| 合計 | 6卓 |

これ以外のテーブルは当日来店客用に残し、AIは使用しない。

**デモ・検証方式**

- 開発・発表の主経路は Connect WebRTC（localhost）。
- Connect のウィジェットを使う場合は、許可ドメインに `http://localhost:3000` を登録する（`127.0.0.1` は別ホスト扱いで読み込まれない）。
- 人間引き継ぎデモは、外部転送で自分のスマホ等へ着信させる（番号を取得できない場合はエージェント画面で応答する）。
- 実電話番号の取得は並行調査するが、取得できない場合でもMVPは成立させる。

**差別化仮説に関わる確認**

- 初期設定項目を最小限に絞る（営業時間・席・AI予約枠・標準利用時間・FAQ）。
- 「簡単さ」は後工程の飾りではなく、設定項目の少なさと画面の分かりやすさで検証する対象とする。
- 店舗アカウント：
  - **初期（MVP）**：運営者（自分）がデモ用店舗を登録する。
  - **完成系**：店舗が自分でアカウントを作成し、利用申し込みできる。**利用開始には運営者の承認を必須とする。**

### Phase 1：予約判定APIを作る（画面より先・電話より先）

電話も管理画面も、ここに依存する。**最初にここを完成させる。**

**実装構成**

- API Gateway + Python Lambda + DynamoDB
- 店舗・席・予約は最初から tenantId を持つ
- 初期データはシード（デモ用1店舗）で投入してよい
- React管理画面はこの段階では本格実装しない（必要ならAPI動作確認用の最小呼び出しでよい）

**実装するもの**

- 店舗設定の取得（営業時間・標準利用時間・AI予約枠）
- 空席確認API
- 予約確定API（仮確保が必要ならその手順も含む）
- 営業時間・定休日・最終受付時刻・15分刻みの検証
- 利用時間を考慮した重複判定
- DynamoDBの条件付き書き込み等による二重予約防止
- 店舗ID・日付・テーブル等を使ったアクセスパターン設計

予約変更・キャンセルのAPIは初期版では作らない（Phase 0の決定どおり後回し）。

**判定手順**

1. 店舗ID（tenantId）を確定する。
2. 予約希望日時・人数を受け取る。
3. 開始時刻が15分刻みで、営業日の営業時間内かつ最終受付時刻以前であることを確認する。
4. 人数に対応するテーブル種別を決める。
5. 店舗設定の標準利用時間から終了時刻を計算する。
6. AI予約用に開放されたテーブルだけを検索する。
7. 既存予約と時間が重なるテーブルを除外する。
8. 空いているテーブルがあれば確定処理を行う。
9. 確定直前に空席を再確認する（条件付き更新）。
10. 成功・満席・受付不可・人間対応の結果を返す。

**重要な技術課題：二重予約防止**

同じ時間帯に複数の通話・リクエストが来ると、2件が同じ空席を同時に見つける可能性がある。検索しただけで予約確定にせず、DB更新時に条件付き書き込みやトランザクション等を使って、同じ席を重複確保できないようにする。

**完了条件**

- APIだけで空席確認・予約確定ができる。
- 同じ席・同じ時間帯の予約を重複登録できない。
- 予約終了後の時間帯は再利用できる。
- AI予約枠外の席は確保されない。
- 7人以上など対応外は人間対応結果を返す。
- 終了時刻が店舗設定の標準利用時間どおりに計算される。
- 定休日・営業時間外・最終受付時刻より後・15分刻みでない開始時刻は確定されない。
- tenantId なし／別tenantId では対象店舗の予約を操作できない。

### Phase 2：Connect WebRTCで電話受付を作る

予約判定APIが動いてから、音声・会話を接続する。**管理画面より先に電話経路を通す。**

**役割分担（ここで固定）**

| 担当 | やること | やらないこと |
|---|---|---|
| Amazon Connect | 着信、店名の案内、1/2の振り分け、転送、通話の記録 | 会話の中身の判断 |
| Amazon Lex（ja_JP） | 音声→文字（音声認識）、会話のターン管理、毎ターン Lambda に文字列を渡す | 予約可否の判断 |
| Amazon Bedrock | 文字列から日時・人数・名前を取り出す、FAQ に基づく回答文を作る | 音声認識、空席判断、予約確定、日付・時刻の最終決定 |
| Lambda（Python のコード） | 店舗特定、日付の確定と検証、空席確認・予約確定 API の呼び出し、次に何を聞くかの決定 | — |
| DynamoDB | 店舗設定・FAQ・予約・通話履歴 | — |

- **Bedrock は文字起こしをしない。** 音声を文字にするのは Lex（音声認識）。Bedrock は文字になったものを読む。
- フローは **全店共通の1本**。店名・FAQ・転送先は、着信先（実電話は `$.SystemEndpoint.Address`、WebRTC は着信先番号が無いのでデモ用の固定番号）から Lambda で引いて差し替える。着信は普通の電話・非通知・WebRTC の3種類を店舗特定の Lambda で判定する。非通知は客の番号を空のまま扱い（予約は番号なしで受け付ける）、WebRTC は番号が無いのでデモ用の固定値で埋める（固定値は保存しない）。店ごとにフローを作らない。

**電話フロー**

1. 着信を受ける（WebRTC または実電話）。
2. Lambda で店舗を特定し、店名・営業時間・転送先をコンタクト属性に入れる。
3. 「お電話ありがとうございます。〇〇店です。ご予約の方は1を、それ以外のお問い合わせは2を押してください。」
   - ボタン（DTMF）に加えて「予約」「問い合わせ」の発話でも分岐できるようにする（同じ入力ブロックで Lex に両方受けさせる）。
   - Connect 標準の通信ウィジェット（`demo/webrtc/`）で数字キーが出るかは実機で確認する。出なければ、自前のキーパッドから参加者 API（`CreateParticipantConnection` → `SendMessage`、`audio/dtmf`）で送る。発話でも分岐できれば最初はそれで足りる。
4. **1：予約**（下記「予約の会話」）
5. **2：問い合わせ**（下記「問い合わせの会話」）
6. どちらの途中でも、対応外・聞き取り失敗が続いたら人間へ引き継ぐ。
7. 通話履歴（文字起こし・結果）を tenantId 付きで保存する。要約は通話終了後に非同期で作る。

**予約の会話（1）**

Bedrock を使う。理由は、客が「来週の金曜、7時半くらいに大人3人と子ども1人」のように **1回の発話で複数の項目を自由な言い方で話す** ため。Lex の固定スロットだけでは取りこぼしやすい。ただし Bedrock は「取り出す係」にとどめ、決めるのはコード。

1. 「ご希望の日時と人数をお話しください。」
2. Lex が文字にした発話を Lambda に渡す。
3. Lambda が Bedrock に、発話・今日の日付と曜日・これまでに聞けた項目を渡し、`{date, time, partySize, name}` を JSON で返させる（分からない項目は空）。
4. Lambda（コード）が検証する。
   - 日付を確定する（相対表現は Bedrock の候補を受け取り、コードで今日からの日付として妥当か確認）
   - 15分刻みでなければ「19時15分と19時30分、どちらがよろしいですか」と聞き直す
   - 定休日・営業時間外・最終受付後なら、その場で伝える
   - 7人以上は人間へ引き継ぐ
5. 足りない項目だけを聞く（質問文はコードの定型文。Bedrock に自由に作らせない）。
6. 空席確認 API を呼ぶ。満席なら、コードが近い空き時間を探して提案する。
7. **固定の文で復唱する**：「11月21日 金曜日 19時30分から、4名様、ヤマダ様でよろしいですか。」
   - 日付は必ず曜日付きで読み上げる（相対日付の取り違えを客に気づかせるため）
8. 「はい」で予約確定 API を呼ぶ。**確定 API が成功したときだけ**「ご予約を承りました」と言う。
9. 名前は音声認識で漢字にできないことが多いので、カタカナの読みで保存する。電話番号は実電話なら着信番号を使い、WebRTC では聞かない（任意）。

**問い合わせの会話（2）**

1. 「ご用件をお話しください。」
2. Lex が文字にした発話を Lambda に渡す。
3. Lambda が DynamoDB からその店の FAQ・営業時間・住所などを取り、発話と一緒に Bedrock に渡して回答文を作らせる。
   - 1店分の FAQ は小さいので、プロンプトに直接入れる。Bedrock のナレッジベース（ベクトル検索）は初期版では使わない。
   - 指示：「渡した情報にないことは答えない。分からなければ『確認いたします』と言う」
4. 回答を読み上げ、「ほかにご用件はありますか」でもう一度受ける。
5. 予約の話だと判断したら（Bedrock の分類 + キーワード）、予約の会話へ移る。
6. 答えられない質問は、内容を記録して人間へ引き継ぐ（または折り返し扱い）。

**応答時間の制約**

- Connect の「Lambda 呼び出し」ブロックは同期で最大8秒。Lex 経由で呼ぶ Lambda は最大30秒。
- Bedrock は Lex のコードフック（Lambda）の中で呼ぶ。モデルは応答の速い小型のもの（Claude Haiku 系 / Amazon Nova Lite など）にし、1ターン数秒に収める。
- 1ターンで Bedrock を呼ぶのは1回までにする。

**Lex の生成AI機能について**

- 日本語（ja_JP）でも、Lex の「補助付きスロット解決」（Bedrock で日付・数値・はい/いいえの聞き取りを補う）が使える。復唱後の「はい/いいえ」はこれで受ける。
- Lex の `QnAIntent` は Bedrock のナレッジベースが前提なので、初期版では使わない（上記のとおり Lambda から Bedrock を直接呼ぶ）。

**AIの安全ルール**

- 登録されていない営業時間・料金・サービスを推測で答えない。
- 名前、日時、人数は予約確定前に復唱する。
- 聞き取れない場合は再確認する。
- **7人以上の予約や特殊な要望は、外部転送で人間（自分の電話）へ引き継ぐ。**
- DBの予約確定が成功していないのに、予約完了と案内しない。
- 利用時間は店舗が設定した標準利用時間を使い、AIが独自に変更しない。

**完了条件**

- localhost の WebRTC から予約会話ができる。
- 冒頭で着信先に応じた店名が読み上げられ、1/2（または発話）で予約と問い合わせに分かれる。
- 「来週金曜の7時半に4人」のような1回の発話から日時・人数を取り出せる。
- 問い合わせに FAQ の範囲で答え、FAQ にないことは推測で答えない。
- 予約判定API経由でDBに予約が残る。
- 満席・対応外で誤確定しない。
- 対応外のとき人間へ引き継げる（Connect 側の番号があれば外部転送で自分の電話、なければエージェント画面で応答）。
- 通話履歴が tenantId 付きで保存される。

### Phase 3：予約管理Webアプリを載せる

電話で予約が残るようになったあと、店舗側の確認・設定・手動操作の画面を作る。

**実装構成**

- React + TypeScriptで管理画面を作る。
- ReactからAPI GatewayのHTTP APIを呼び出す。
- 予約の作成・空席確認は Phase 1 のAPIを再利用する。

**実装するもの**

- 店舗管理者ログイン（初期はデモ用アカウントでも可）
- 店舗情報・営業時間の登録・編集
- テーブル構成・AI予約枠の設定
- 標準利用時間の設定
- FAQの登録
- 予約一覧
- 手動予約登録
- （余力があれば）通話履歴の閲覧

予約の変更・キャンセルは後回し。必要になったら最小限の状態変更から足す。

**導入の簡単さ（差別化仮説）をここで検証する**

- 初期設定項目が少なく、迷わず埋められるか。
- 予約一覧が初めて使う人にも分かるか。
- 可能なら店主・スタッフに操作してもらい、詰まる箇所を直す。

**完了条件**

- 電話で入った予約が管理画面に表示される。
- 管理画面から手動予約できる。
- 設定変更（営業時間・AI枠・標準利用時間）が電話側の判定・回答に反映される。
- 他店舗のデータが見えない。

### Phase 4：複数店舗対応の拡張

Phase 1〜3 では tenantId 設計済み・店舗1件運用。ここでは店舗追加と運用面を拡張する。

**実装するもの**

- 複数店舗アカウントとユーザー認証の本整備
- 2店舗目以降の着信先の登録（着信先と tenantId の対応表そのものは Phase 2 で作る）
- 店舗ごとのFAQ・営業時間・席構成・AI予約枠・標準利用時間
- 運営者用の店舗管理機能（必要な範囲）
- **完成系に向けた店舗セルフ申し込み**（店舗が自分でアカウント作成・申し込み → **運営者承認必須**）

**着信先から店舗を特定する流れ**

1. Amazon Connectで着信を受ける（WebRTC含む）。
2. 着信先の識別子を取得する（WebRTC は通話開始時に渡した店舗識別子、実電話は Connect 側の番号）。
3. Lambdaで着信先の識別子と tenantId の対応を検索する。
4. tenantId を以後の処理に渡す。
5. 対象店舗のデータだけを取得・更新する。

**セキュリティテスト**

- A店ユーザーがB店の予約を見られない。
- APIリクエストのtenantIdを書き換えても他店データへアクセスできない。
- 着信先の識別子と店舗の紐付けを誤ると別店舗のFAQ・予約を使ってしまうため、紐付けを検証する。
- 管理者権限と店舗ユーザー権限を区別する。

### Phase 5：通話履歴・利用量・問い合わせ管理

- 通話履歴
- 文字起こし・要約（取得できる構成にする）
- AI対応完了／人間への引き継ぎ
- 問い合わせの対応状況
- 通話秒数・通話件数
- AI利用量（取得できる場合）

料金計算は後回しでも、利用量の記録は設計時点から行う。月次の集計値だけでなく、通話1件ごとの明細を保存する。

### Phase 6：仕上げ・発表準備

- 入力エラー・通信エラー時の表示
- ログ・例外処理
- 個人情報の取り扱いと保存期間の整理
- デモ用の店舗・FAQ・席設定・予約データを準備
- AWS構成図・DB設計図・シーケンス図を作成
- WebRTC電話デモを複数パターンで確認（実番号があれば実電話も）
- 企業向け説明資料を作成
- 「予約管理システム未導入店向け」というターゲットと、競合GATEとの違いを説明できるようにする

## 4. デモシナリオ

### デモ1：正常な予約（主デモ・WebRTC）

- localhost の WebRTC からA店へ通話する。
- 「明日の19時に4人で予約したい」と伝える。
- AIが名前などを聞き取る。
- 4人用テーブルの空き状況を確認する。
- 店舗設定の標準利用時間（例：120分）で終了時刻を計算する。
- 予約内容を復唱する。
- 予約確定後、A店の管理画面に予約が表示される。

### デモ2：AI予約枠が満席

- 予約希望時間にAI予約用テーブルが空いていない。
- AIが予約を確定しない。
- 別の時間を提案する、または人間へ引き継ぐ。

### デモ3：当日来店客用の席を残す

- 店舗にはAI予約用テーブルと当日来店客用テーブルがある。
- AI予約用テーブルが空いていても、当日来店客用テーブルを予約に使わない。
- 店舗が確保したい当日客用の席が維持される。

### デモ4：利用時間の重複

- 店舗の標準利用時間を120分に設定する。
- 18:00〜20:00に予約が入っている。
- 同じテーブルに19:00開始の予約は入れられない。
- 20:00開始の予約は、同じテーブルで受け付けられる（終了時刻ちょうどから次の予約が入れられる）。

### デモ5：複数店舗・データ分離

- A店向けの着信ではA店の情報で応答する。
- B店向けの着信ではB店の情報で応答する。
- A店の管理者はB店の予約を閲覧できない。

### デモ6：対応範囲外の予約（外部転送）

- 7人以上の予約など、AIが確定できない条件を伝える。
- AIは無理に予約を確定せず、外部転送で自分の電話へ引き継ぐ。
- Connect 側の番号を取得できていない場合は、エージェント画面へ転送して自分が応答する形で見せる。

### デモ7：初期設定の簡単さ（差別化仮説の確認）

- 店舗管理者が営業時間、テーブル、AI予約枠、標準利用時間、FAQを設定する。
- 設定した内容が電話AIの応答・空席判定に反映される。
- 店舗側が迷わず設定できるか、初めて使う人でも操作できるかを確認する。

## 5. 開発上のリスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| Connect WebRTCのローカル検証につまずく | 電話デモが遅れる | Phase 2の早い段階で着信1回を通す。ブラウザ権限・許可ドメイン（`http://localhost:3000`）・エージェント設定を先に確認 |
| AWS電話番号を取得できない | 実電話デモと外部転送ができない | **MVPはWebRTCで成立させる。** 実番号は追加デモ。人間引き継ぎはエージェント画面への転送で代替する |
| AIが日時・人数を誤認識 | 誤予約 | 確定前の復唱、再確認、人間への引き継ぎ |
| 同時着信で二重予約 | 店舗運営に影響 | DB側で条件付き更新・排他制御 |
| 店舗データが混ざる | 情報漏えい | tenantId検証、認可テスト |
| 管理画面を先に作り込みすぎる | 電話デモが間に合わない | Phase 3まで画面を本格実装しない |
| 電話会話だけ先に作る | 予約がDBに残らない・判定が後付けになる | Phase 1の判定API完成を電話接続の前提にする |
| AWS利用料が想定を超える | 制作費の負担 | 利用上限・ログ・予算アラートを検討 |
| 予約ルールが複雑になる | 開発遅延 | 初期版はテーブル種別と人数・時間のルールを限定 |
| 外部台帳との連携がない | 実店舗導入に制約 | 就職作品の初期版では自作台帳の完成を優先し、制約として説明 |
| 競合と機能が重なる | 事業上の差別化が弱い | 未導入店の導入障壁を調査し、初期設定・操作の簡単さを検証 |
| セルフ設定が難しい | ターゲットに使ってもらえない | 初期設定項目を絞り、Phase 3で操作テストを行う |

### 電話デモについて

- **主経路：** Amazon Connect の WebRTC を localhost で使い、ブラウザから通話・予約デモを行う。
- **副経路：** 日本国内の電話番号が取得でき、個人開発の検証条件を満たす場合は実電話デモを追加する。
- Connect の日本の番号（050・03・0120 など）は事業用に限られ、取得には会社の登録書類などの提出が求められる。個人では取得できない可能性が高い前提で計画する。
- 申請・審査・クォータ引き上げは承認されるとは限らないため、実電話が使える前提で計画しない。
- 外部転送も Connect 側の番号を発信者番号として使うため、番号がなければ使えない。その場合の人間引き継ぎはエージェント画面への転送で行う。

## 6. データとして最低限保存するもの

詳細なキー設計・アクセスパターン・二重予約防止は **`DB設計.md`** を正とする。ここでは保存対象の概要のみ書く。

### 店舗
- tenantId
- 店舗名
- 営業時間・定休日
- 着信先の識別子（店舗あたり1つ・全店で重複不可）／人間引き継ぎ用転送先（店舗あたり1つ。デモ店は開発者の番号）
- FAQ・店舗情報
- 標準利用時間（初期120分）・開始刻み（15分）

### テーブル・席
- tenantId
- tableId
- テーブル種別・定員（卓単位）
- AI予約対象かどうか
- 利用可能状態

### 予約
- tenantId
- reservationId
- 日付・開始時刻・終了時刻
- 人数
- 顧客名・電話番号
- 使用テーブルID
- 予約状態
- 登録元（AI／手動）

### 占有スロット（空席・二重予約防止）
- tenantId / tableId / 日付 / 15分刻み時刻
- 紐づく reservationId

### 通話
- tenantId
- callId
- かけてきた番号（callerNumber。WebRTC では取得できない）／着信先（calledNumber）
- 開始・終了時刻・通話秒数
- 着信／発信（WebRTC含む）
- 転送有無・転送先
- 対応結果
- AI利用量（取得できる場合）

## 7. 就職作品イベントで説明するポイント

発表では機能一覧だけでなく、技術的に難しかった点と解決方法を説明する。

1. **なぜこのターゲットか**：予約管理システム未導入で、紙・Excel管理をしている小規模店を想定した理由。
2. **なぜ自社台帳を持つか**：既存予約台帳を前提にせず、電話受付から予約管理までを一つのサービスで完結させるため。
3. **競合と何が違うか**：GATEも一体型であることを認めたうえで、初めて導入する店舗にとって設定・操作が簡単かを検証し、作品で示す。
4. **なぜ判定APIを先に作ったか**：電話と管理画面が同じ予約処理を共有し、会話デモだけで終わらせないため。
5. **なぜWebRTCでデモするか**：実番号取得に依存せず、電話→予約確定の核を確実に見せるため。
6. **着信先からどう店舗を特定するか**：着信先の識別子をキーに対応表を引き、店舗設定を取得する。
7. **どう二重予約を防ぐか**：予約検索だけでなく、確定時のDB更新で競合を制御する。
8. **どう当日客の席を残すか**：店舗がAI予約対象の席を指定し、AIはその範囲だけを使用する。
9. **利用時間をどう扱うか**：店舗が初期設定した標準利用時間から終了時刻を計算する。
10. **AIが間違えたらどうするか**：確定前の復唱、再確認、対応範囲外の人間引き継ぎ。
11. **AWSをどう使ったか**：Connect・Lambda・DB・認証・AIをどう連携したか。

## 9. 開発の最重要方針

**機能を増やすより、WebRTC電話を受けて予約を確定し、その予約が正しい店舗のデータとして安全に残るところまで完成させる。**

順序は次で固定する。

1. **予約判定API**（tenantId込み）
2. **Connect WebRTC電話**（判定APIを呼ぶ）
3. **管理画面**（結果の確認・設定・手動予約）
4. **複数店舗の運用拡張**
5. 利用量・問い合わせ・発表仕上げ

外部予約台帳連携、Webサイト差分検出、詳細な料金計算などは、基本機能が完成してから検討する。

また、作品の企画説明では「競合がいない」「一体型だから独自」と主張しない。予約管理システム未導入の店舗にとって、初めて導入しやすく、設定・操作が簡単なサービスになっているかを実際に検証する。
