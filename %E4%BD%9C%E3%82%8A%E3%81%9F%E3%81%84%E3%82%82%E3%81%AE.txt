## 1. 企画概要

予約管理システムをまだ導入していない小規模飲食店向けに、**AI電話受付と予約管理を一体化した、複数店舗対応のクラウドサービス（SaaS）**を開発する。

主な対象は、電話で予約を受け付け、紙の予約台帳やExcel・Googleスプレッドシートなどで管理している店舗。既存の予約管理システムを前提にせず、電話受付から空席確認、予約確定、予約台帳への登録までを1つのサービス内で完結させる。

顧客からの電話をAIが受け、店舗情報への質問に回答する。予約希望の場合は、日時・人数・名前・電話番号などを聞き取り、店舗がAI予約用に開放した席と予約時間を照合する。条件を満たす場合は予約を登録し、管理画面に反映する。

店舗は管理画面から営業時間、FAQ、席構成、AI予約に使う席数、標準利用時間、予約状況などを管理できる。複数の店舗が同じシステム基盤を利用するが、店舗ごとの設定・予約・通話履歴は分離する。

### 解決したい課題

- 接客・調理中に電話へ出られず、予約や問い合わせを取りこぼす。
- 電話で受けた予約を紙や表計算ソフトへ転記する手間がある。
- 予約時間や人数の聞き間違い、記入漏れが発生する可能性がある。
- 予約客だけで席を埋めると、予約なしで来店する客の席が不足する。
- 予約管理システム未導入の店舗では、AI電話だけを導入しても予約を記録・管理する仕組みが別途必要になる。
- 電話AIと予約台帳が別サービスの場合、契約・設定・管理先が分かれ、情報の二重管理が発生する可能性がある。

本作品では、**予約管理システムを持たない店舗が、電話受付と予約管理を別々に導入せず、最初から一体の仕組みとして利用できること**を中心価値とする。

ただし、AI電話と自社予約台帳を一体提供する競合（GATEなど）はすでに存在するため、「一体化」だけを独自性とはしない。導入対象を初めて予約管理をデジタル化する小規模店に絞り、導入・設定・日常操作の簡単さを差別化仮説として検証する。

## 2. 想定ターゲット

### 主な対象

- 個人経営、または小規模チェーンの飲食店
- 電話予約を受け付けている店舗
- **予約管理システムをまだ導入していない店舗**
- 紙の予約台帳やExcel・Googleスプレッドシートで予約を管理している店舗
- 少人数で接客・調理・電話対応を兼任している店舗
- 既存システムの高度な機能や外部連携までは必要としていない店舗
- まずは電話予約と基本的な予約台帳を簡単にデジタル化したい店舗

### 対象外になりやすい店舗

- 予約をほとんど受け付けていない店舗
- 来店順で案内することが中心で、席予約を管理しない店舗
- 既存の予約台帳や複数の予約経路を高度に統合する必要がある店舗（初期版では外部連携を想定しない）
- 大規模チェーンで本部一括管理、複雑な配席、複数媒体・POS・CRM連携が必須の店舗

### 利用者

1. **店舗管理者**：店舗情報、席構成、AI予約枠、FAQ、予約を管理する。
2. **電話をかける顧客**：店舗への質問や予約を電話で行う。
3. **サービス運営者**：店舗アカウントや利用状況を管理する。

## 3. サービスの基本機能

### 3.1 店舗登録・ログイン

- 店舗がサービスの利用を申し込む。
- 店舗名、住所、電話番号、営業時間などを登録する。
- 管理者が店舗アカウントを管理する。
- 店舗ごとに管理画面へログインできる。
- 店舗ごとのデータを分離する。

※一般公開のセルフサインアップや審査フローをどこまで実装するかは未決定。作品では管理者がデモ用店舗を登録する方式でもよい。将来的には、店舗自身が必要事項を入力して利用開始できる導入フローを目指す。

### 3.2 AI電話受付

- Amazon Connectで着信を受ける。
- 着信先電話番号から対象店舗を特定する。
- 店舗の営業時間、住所、FAQ、サービス情報などを取得する。
- AIが店舗情報に基づいて回答する。
- AIが回答できない、または情報に確信を持てない場合は、推測で答えず人間へ引き継ぐか、問い合わせとして記録する。
- 必要に応じて店舗の電話番号へ転送する方式を検討する。

### 3.3 AI電話予約

AIは顧客との会話から、少なくとも次の情報を聞き取る。

- 予約希望日
- 予約希望時刻
- 人数
- 予約者名
- 折り返し可能な電話番号（必要な場合）

聞き取った内容を顧客に読み上げて確認し、予約条件を満たす場合に確定する。

### 3.4 席の設定とAI予約枠

店舗は初期設定時に、席・テーブルの構成と、そのうちAIが予約に使ってよい席を設定する。

**設定例（AI予約に開放する席）**

| テーブル種別 | AI予約に開放する数 |
|---|---:|
| 4人用テーブル | 4卓 |
| 6人用テーブル | 2卓 |
| 合計 | 6卓 |

店舗にこれ以外の席がある場合、その席は予約なしの来店客向けに残す。AIは設定されたAI予約枠の外にある席を勝手に予約しない。

人数とテーブルの対応は、現時点での基本案として次のようにする。

- 4人の予約：4人用テーブルを使用する。
- 6人の予約：6人用テーブルを使用する。
- **7人以上の予約：AIだけで確定せず、人間へ引き継ぐ。**
- 1〜3人、5人の場合の割り当てや、複数卓を組み合わせる扱いは詳細未決定。実装前に店舗ルールとして決める。

### 3.5 予約時間・重複判定

- **店舗が初期設定で標準利用時間を決める**（例：120分）。
- 利用時間はAIが推測して決めるものではなく、顧客が毎回指定するものでもない。
- 予約開始時刻と店舗が設定した利用時間から終了時刻を計算する。
- 例：標準利用時間が120分の場合、18:00開始の予約は20:00終了、19:00開始の予約は21:00終了として空席判定する。
- 既存予約と時間が重なるAI予約用テーブルは使用できない。
- 利用時間が終了した後の時間帯では、同じテーブルを再び予約候補にできる。
- 予約の確認から確定までの間に別の予約が入る可能性があるため、確定時に空席を再確認し、二重予約を防止する。
- AI予約枠が埋まっている場合は、別時間を提案するか人間へ引き継ぐ。

**重要：** 「6卓をAI予約に開放する」は、店舗全体の全席を予約で埋めてよいという意味ではない。AI用に設定した席だけを使用し、その他の席は当日来店客用として残す。

### 3.6 予約管理画面

店舗管理者は次の情報を確認・操作できる。

- 日付・時間ごとの予約一覧
- 予約者名、人数、電話番号
- 使用テーブル
- 予約の状態（確定、変更、キャンセル等）
- 店舗の席構成とAI予約枠
- 標準利用時間
- 店員による手動予約登録
- AI電話の通話履歴・対応結果

### 3.7 問い合わせ・通話履歴

- 問い合わせ日時
- 通話内容の文字起こし
- AIによる要約
- AIが回答したか、人間へ引き継いだか
- 対応状況（未対応、対応中、対応済み等）

営業時間外の電話は、要件を聞き取って記録し、後から店舗が確認できるようにする。営業時間開始時の自動通知は追加候補とする。

### 3.8 利用量記録

将来的な料金管理に備え、通話単位の利用量を記録する。

- 店舗ID、通話ID
- 通話開始・終了時刻、通話秒数
- 着信・発信の区分
- 転送の有無・転送時間
- AIモデルの入出力トークン数（取得できる場合）
- 音声認識・音声合成等の利用量（取得できる場合）

月次集計・概算料金表示は追加候補。実際のAWS請求額と完全一致するとは限らないため、表示する場合は「概算」とする。

## 4. 複数店舗対応（マルチテナント）

**最終的には複数店舗対応を目指す。** ただし、開発は1店舗の予約フローを完成させてから複数店舗へ拡張する。

### 店舗ごとに分離するデータ

- 店舗情報・営業時間
- FAQ・AI回答設定
- 電話番号との紐付け
- 席構成・AI予約枠・標準利用時間
- 予約情報
- 通話履歴・文字起こし・要約
- 利用量

### 必須のセキュリティ要件

- すべての店舗データに店舗ID（tenantId）を関連付ける。
- ログインユーザーが所属する店舗のデータだけを参照・更新できるようにする。
- 電話番号から店舗を特定した後は、その店舗の情報だけをAIに渡す。
- A店の管理画面からB店の予約・通話履歴を閲覧できないようにする。
- サーバー側でも権限と店舗IDを検証する。画面上で隠すだけの制御にしない。

### 電話着信時の流れ

1. 顧客が店舗の電話番号へ発信する。
2. Amazon Connectが着信を受ける。
3. 着信先番号を取得する。
4. Lambdaが電話番号と店舗IDの対応を検索する。
5. 対象店舗の営業時間・FAQ・予約設定を取得する。
6. AIが応答・予約受付を行う。
7. 通話・予約データを対象店舗IDと紐付けて保存する。

## 5. 技術構成案（AWS中心）

### Web管理画面・予約APIの基本構成（採用方針）

| 技術 | 想定する役割 |
|---|---|
| React | 予約一覧、予約登録、店舗設定などの画面 |
| TypeScript | React側の開発言語。画面で扱うデータの型を明確にする |
| Amazon API Gateway | ReactからのHTTPリクエストを受け付け、Lambdaへ渡す |
| AWS Lambda（Python） | 予約登録、空席確認、予約変更、キャンセル、入力検証など |
| Python標準機能 | Lambdaの処理を実装。FastAPI・FlaskなどのWebフレームワークは初期構成では使用しない |
| boto3 | PythonからDynamoDBなどのAWSサービスを操作するAWS SDK |
| Amazon DynamoDB | 店舗、席、予約、FAQ、通話履歴、利用量を保存 |

基本的なリクエストの流れは、Reactの管理画面 → API Gateway → Pythonで実装したLambda → DynamoDBとする。LambdaはHTTPサーバーとして常時起動するのではなく、API Gatewayから呼び出されたときに処理を実行する。

予約処理はWeb画面からの手動登録と電話AIからの自動予約で共通利用できるように設計する。電話AI側も、同じ予約判定・登録処理を呼び出す方針とする。

### 電話AI・認証・補助機能の構成候補

| 技術 | 想定する役割 |
|---|---|
| Amazon Connect | 電話番号、着信、通話フロー、転送 |
| Amazon Lex | 音声認識・会話フロー（採用範囲は要検討） |
| Amazon Bedrock | FAQ回答、自然言語理解の補助、要約 |
| Amazon Cognito | 店舗ユーザーの認証 |
| Amazon S3 | 音声データ等を保存する場合に利用 |
| Amazon EventBridge | 定期処理や通知を追加する場合に利用 |

※React・TypeScript・API Gateway・Python Lambda・DynamoDBを基本構成とする。Connect・Lex・Bedrockの役割分担、音声の入出力方式、料金、リージョンや電話番号取得条件は検証して確定する。Lambdaの予約確定処理では、同時予約による二重確保を防ぐため、DynamoDBの条件付き書き込みやトランザクション等を設計する。

### 予約データ設計で重視すること

- 店舗IDと予約IDを紐付ける。
- 予約開始・終了時刻、人数、使用テーブル、状態を記録する。
- 予約確定処理で同じ席・同じ時間帯を二重に確保できないようにする。
- 予約変更・キャンセル時に席の空き状況が正しく更新されるようにする。
- 複数の電話が同時に来ても予約枠が壊れないよう、DB側で排他・条件付き更新等を設計する。

## 6. 作品としてのアピールポイント

- Amazon Connectを利用した実際の電話システム
- 音声AIによる予約情報の聞き取り
- 席数・店舗設定の利用時間を考慮した予約判定
- 二重予約を防止するDB設計
- AI予約用の席と当日来店用の席を分ける業務設計
- 複数店舗対応のマルチテナント設計
- 店舗ごとの認証・アクセス制御・データ分離
- 電話から予約DB、管理画面までつながる一連の業務自動化
- 通話・AI利用量の記録
- 予約管理システム未導入店を想定した、初期設定・日常操作が分かりやすいUI設計

AWSのサービス数を増やすこと自体ではなく、**電話・予約・データ分離・同時実行という課題をどう設計して解決したか**を説明できることを重視する。

## 8. 企画説明文（仮）

予約管理システムをまだ導入していない小規模飲食店向けに、AI電話受付と予約管理を一体化した複数店舗対応SaaSを開発する。紙やExcelなどで予約を管理している店舗が、別々の電話AIサービスと予約台帳を組み合わせることなく、電話受付から予約登録・管理までを一つのサービスで行えることを目指す。顧客からの電話にAIが応答し、店舗情報に関する質問への回答や予約受付を行う。予約時には、店舗がAI予約用に設定したテーブルと、店舗が初期設定した標準利用時間を照合し、空席がある場合のみ予約を確定する。AI予約用の席以外は予約なしの来店客向けに残すことができる。店舗は管理画面から予約・席構成・通話履歴を管理でき、複数店舗が同じ基盤を利用しながらデータを安全に分離する。AWSを活用し、電話受付から予約登録・管理までの業務を自動化することを目指す。
