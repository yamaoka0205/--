# 作る道筋（開発計画）
## 予約管理システム未導入の小規模飲食店向け AI電話受付・予約管理SaaS

- 制作形態：個人制作
- 目標：就職作品イベントで、企業の技術者に電話デモと管理画面を見せ、設計意図を説明できる状態にする。
- 方針：**まず1店舗で電話から予約確定までを完成させ、その後に複数店舗対応へ拡張する。**
- ターゲット：予約管理システムをまだ導入しておらず、紙・Excel等で予約を管理している小規模飲食店。

### 採用する基本技術構成

- フロントエンド：React ＋ TypeScript
- API受付：Amazon API Gateway
- バックエンド：AWS Lambda（素のPython）
- データベース：Amazon DynamoDB
- PythonからAWSサービスを操作：boto3
- 初期構成ではFastAPI・FlaskなどのWebフレームワークは使用せず、API GatewayからLambdaのハンドラーを直接呼び出す。
- Reactの管理画面からの予約操作と、電話AIからの予約操作は、可能な限り同じ予約判定・登録処理を利用する。

基本的な処理経路は「React管理画面 → API Gateway → Python Lambda → DynamoDB」。Lambdaは常時起動するWebサーバーではなく、API Gateway等から呼び出されたときに処理を実行する。

---

## 1. 完成目標（MVP）

最初の完成ラインは、次の一連の流れが実際に動くこと。

1. 店舗管理者がログインする。
2. 店舗情報・営業時間・席構成・AI予約枠・標準利用時間を設定する。
3. 顧客が店舗の電話番号へ電話する。
4. AIが予約希望日時・人数・名前などを聞き取る。
5. AIが店舗設定の利用時間を使って終了時刻を計算し、予約可能な席を確認する。
6. 予約可能なら内容を復唱して確定する。
7. 予約情報がDBへ登録される。
8. 店舗管理画面に予約が表示される。
9. 別店舗のアカウントでは、その予約を閲覧できない。

この流れを最優先にし、Webサイト差分検出や高度な料金計算などは後回しにする。

## 2. 開発フェーズ

### Phase 0：要件を確定する

実装前に、予約ルールを具体化する。

- 店舗の全テーブル数
- AI予約に開放するテーブル数
- 当日来店客用に残すテーブル数
- テーブルごとの定員
- 人数とテーブルの割り当て
- **店舗が初期設定で決める標準利用時間**
- 予約可能な時間帯
- 予約開始時刻の刻み
- 予約変更・キャンセルの扱い
- AIが確定できない場合の引き継ぎ先

**現時点の席設定例**

| 種類 | AI予約に開放する数 |
|---|---:|
| 4人用 | 4卓 |
| 6人用 | 2卓 |
| 合計 | 6卓 |

これ以外のテーブルは当日来店客用に残し、AIは使用しない。4人の予約は4人用、6人の予約は6人用を使用し、**7人以上の予約は人間へ引き継ぐ**。1〜3人・5人の割り当ては実装前に決める。

**利用時間のルール**
- 店舗が初期設定で標準利用時間を設定する（例：120分）。
- AIが利用時間を推測して決めることはしない。
- 顧客が毎回利用時間を指定する方式にもせず、店舗の設定値を使う。
- 例：120分設定なら18:00開始→20:00終了、19:00開始→21:00終了として空席判定する。
- 初期版は店舗ごとの基本利用時間を1つ設定する方式でよい。コース別・曜日別の時間変更は将来の拡張候補。

### Phase 1：予約管理Webアプリを作る（電話AIより先）

先にReactの画面、API Gateway、Python Lambda、DynamoDBで予約の基本動作を完成させる。

**実装構成**
- React + TypeScriptで管理画面を作る。
- ReactからAPI GatewayのHTTP APIを呼び出す。
- API GatewayからPython Lambdaを呼び出す。
- Lambda内で入力検証・予約処理を行い、boto3でDynamoDBを操作する。
- 初期段階ではFastAPI・Flaskを使わず、Lambdaのハンドラー関数でAPIリクエストを処理する。

**実装するもの**
- 店舗管理者ログイン（初期はデモ用アカウントでも可）
- 店舗情報・営業時間の登録
- テーブル構成の登録
- AI予約枠の設定
- 店舗ごとの標準利用時間の設定
- 予約一覧
- 手動予約登録
- 予約の確定・キャンセル
- 予約時間の重複判定

**完了条件**
- 管理画面から手動で予約を登録できる。
- 予約一覧に正しく反映される。
- 利用時間が重なる予約を同じテーブルに登録できない。
- AI予約枠以外のテーブルは予約候補に出ない。
- 標準利用時間を店舗管理者が変更でき、変更後の予約判定に反映される。

### Phase 2：予約判定ロジックを作る

AIを接続する前に、予約判定を独立した処理として実装・テストする。

**判定手順**
1. 店舗IDを確定する。
2. 予約希望日時・人数を受け取る。
3. 人数に対応するテーブル種別を決める。
4. 店舗設定の標準利用時間から終了時刻を計算する。
5. AI予約用に開放されたテーブルだけを検索する。
6. 既存予約と時間が重なるテーブルを除外する。
7. 空いているテーブルがあれば仮確保・確定処理を行う。
8. 確定直前に空席を再確認する。
9. 成功・満席・人間対応の結果を返す。

**重要な技術課題：二重予約防止**

同じ時間帯に複数の電話が来ると、2件が同じ空席を同時に見つける可能性がある。検索しただけで予約確定にせず、DB更新時に条件付き書き込みやトランザクション等を使って、同じ席を重複確保できないようにする。

DynamoDBを使う場合、予約検索に必要なデータの持ち方や時間帯の表現を先に設計する。単純な全件検索に頼らず、店舗ID・日付・テーブル等を使ったアクセスパターンを決める。

**完了条件**
- 同じ席・同じ時間帯の予約を重複登録できない。
- 予約終了後の時間帯は再利用できる。
- AI予約枠外の席は確保されない。
- 7人以上など、対応人数の上限を超えた予約は人間対応になる。
- 予約終了時刻が店舗設定の標準利用時間どおりに計算される。

### Phase 3：AI電話受付を作る

予約管理が動いてから音声AIを接続する。

**想定技術**
- Amazon Connect：着信・電話フロー
- Amazon Lex：音声認識・会話制御の候補
- Amazon Bedrock：自然言語理解の補助・回答生成の候補
- AWS Lambda（Python）：店舗情報取得、予約判定処理との連携。Web管理画面と共通の予約処理を利用する
- Amazon DynamoDB：店舗情報・予約・通話履歴

**電話フロー**
1. 着信を受ける。
2. 店舗を特定する。
3. 用件を確認する（店舗への質問／予約／その他）。
4. 店舗情報の質問なら、登録済みFAQを参照して回答する。
5. 予約なら必要項目を順番に聞き取る。
6. 聞き取った内容を復唱する。
7. 予約判定処理を呼び出す。
8. 空席があれば予約確定を案内する。
9. 満席なら別時間を提案するか、人間へ引き継ぐ。
10. 通話履歴を保存する。

**AIの安全ルール**
- 登録されていない営業時間・料金・サービスを推測で答えない。
- 名前、日時、人数は予約確定前に復唱する。
- 聞き取れない場合は再確認する。
- **7人以上の予約や特殊な要望は人間へ引き継ぐ。**
- DBの予約確定が成功していないのに、予約完了と案内しない。
- 利用時間は店舗が設定した標準利用時間を使い、AIが独自に変更しない。

### Phase 4：複数店舗対応（マルチテナント）

1店舗での電話予約が動作したら複数店舗に拡張する。

**実装するもの**
- 店舗アカウントとユーザー認証
- tenantIdによるデータ分離
- 店舗ごとの電話番号とtenantIdの対応表
- 店舗ごとのFAQ・営業時間・席構成・AI予約枠・標準利用時間
- 店舗ごとの予約・通話履歴
- 運営者用の店舗管理機能（必要な範囲）

**着信先から店舗を特定する流れ**
1. Amazon Connectで着信を受ける。
2. 着信先番号を取得する。
3. Lambdaで電話番号とtenantIdの対応を検索する。
4. tenantIdを以後の処理に渡す。
5. 対象店舗のデータだけを取得・更新する。

**セキュリティテスト**
- A店ユーザーがB店の予約を見られない。
- APIリクエストのtenantIdを書き換えても他店データへアクセスできない。
- 電話番号と店舗の紐付けを誤ると別店舗のFAQ・予約を使ってしまうため、紐付けを検証する。
- 管理者権限と店舗ユーザー権限を区別する。

### Phase 5：通話履歴・利用量・問い合わせ管理

- 通話履歴
- 文字起こし・要約（取得できる構成にする）
- AI対応完了／人間への引き継ぎ
- 問い合わせの対応状況
- 通話秒数・通話件数
- AI利用量（取得できる場合）

料金計算は後回しでも、利用量の記録は設計時点から行う。月次の集計値だけでなく、通話1件ごとの明細を保存する。

### Phase 6：仕上げ・発表準備

- 入力エラー・通信エラー時の表示
- ログ・例外処理
- 個人情報の取り扱いと保存期間の整理
- デモ用の店舗・FAQ・席設定・予約データを準備
- AWS構成図・DB設計図・シーケンス図を作成
- 実際の電話デモを複数パターンで確認
- 企業向け説明資料を作成
- 「予約管理システム未導入店向け」というターゲットと、競合GATEとの違いを説明できるようにする

## 4. デモシナリオ

### デモ1：正常な予約

- A店に電話する。
- 「明日の19時に4人で予約したい」と伝える。
- AIが名前などを聞き取る。
- 4人用テーブルの空き状況を確認する。
- 店舗設定の標準利用時間（例：120分）で終了時刻を計算する。
- 予約内容を復唱する。
- 予約確定後、A店の管理画面に予約が表示される。

### デモ2：AI予約枠が満席

- 予約希望時間にAI予約用テーブルが空いていない。
- AIが予約を確定しない。
- 別の時間を提案する、または人間へ引き継ぐ。

### デモ3：当日来店客用の席を残す

- 店舗にはAI予約用テーブルと当日来店客用テーブルがある。
- AI予約用テーブルが空いていても、当日来店客用テーブルを予約に使わない。
- 店舗が確保したい当日客用の席が維持される。

### デモ4：利用時間の重複

- 店舗の標準利用時間を120分に設定する。
- 18:00〜20:00に予約が入っている。
- 同じテーブルに19:00開始の予約は入れられない。
- 20:00以降の予約は、店舗ルールと準備時間を満たせば候補になる。

### デモ5：複数店舗・データ分離

- A店の番号に電話するとA店の情報で応答する。
- B店の番号に電話するとB店の情報で応答する。
- A店の管理者はB店の予約を閲覧できない。

### デモ6：対応範囲外の予約

- 7人以上の予約など、AIが確定できない条件を伝える。
- AIは無理に予約を確定せず人間へ引き継ぐ。

### デモ7：初期設定の簡単さ（差別化仮説の確認）

- 店舗管理者が営業時間、テーブル、AI予約枠、標準利用時間、FAQを設定する。
- 設定した内容が電話AIの応答・空席判定に反映される。
- 店舗側が迷わず設定できるか、初めて使う人でも操作できるかを確認する。

## 5. 開発上のリスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| AWS電話番号を取得できない | 実電話デモができない | 番号取得条件を早期確認。取得できない場合のデモ方式も検討 |
| AIが日時・人数を誤認識 | 誤予約 | 確定前の復唱、再確認、人間への引き継ぎ |
| 同時着信で二重予約 | 店舗運営に影響 | DB側で条件付き更新・排他制御 |
| 店舗データが混ざる | 情報漏えい | tenantId検証、認可テスト |
| AWS利用料が想定を超える | 制作費の負担 | 利用上限・ログ・予算アラートを検討 |
| 予約ルールが複雑になる | 開発遅延 | 初期版はテーブル種別と人数・時間のルールを限定 |
| 外部台帳との連携がない | 実店舗導入に制約 | 就職作品の初期版では自作台帳の完成を優先し、制約として説明 |
| 競合と機能が重なる | 事業上の差別化が弱い | 未導入店の導入障壁を調査し、初期設定・操作の簡単さを検証 |
| セルフ設定が難しい | ターゲットに使ってもらえない | 初期設定項目を絞り、実際の店主・スタッフに操作テストを行う |

### AWS電話番号について

Amazon Connectで日本国内の電話番号を取得できるか、個人開発者の検証目的で利用できるか、必要書類や事業要件があるかは、開発初期にAWS公式窓口で確認する。申請・審査・クォータ引き上げは承認されるとは限らない。番号取得が確定する前に、実電話が必ず使える前提で計画しない。

## 7. 就職作品イベントで説明するポイント

発表では機能一覧だけでなく、技術的に難しかった点と解決方法を説明する。

1. **なぜこのターゲットか**：予約管理システム未導入で、紙・Excel管理をしている小規模店を想定した理由。
2. **なぜ自社台帳を持つか**：既存予約台帳を前提にせず、電話受付から予約管理までを一つのサービスで完結させるため。
3. **競合と何が違うか**：GATEも一体型であることを認めたうえで、初めて導入する店舗にとって設定・操作が簡単かを検証し、作品で示す。
4. **電話番号からどう店舗を特定するか**：着信先番号をキーに店舗設定を取得する。
5. **どう二重予約を防ぐか**：予約検索だけでなく、確定時のDB更新で競合を制御する。
6. **どう当日客の席を残すか**：店舗がAI予約対象の席を指定し、AIはその範囲だけを使用する。
7. **利用時間をどう扱うか**：店舗が初期設定した標準利用時間から終了時刻を計算する。
8. **AIが間違えたらどうするか**：確定前の復唱、再確認、対応範囲外の人間引き継ぎ。
9. **AWSをどう使ったか**：Connect・Lambda・DB・認証・AIをどう連携したか。

## 9. 開発の最重要方針

**機能を増やすより、電話を受けて予約を確定し、その予約が正しい店舗の管理画面に安全に反映されるところまで完成させる。**

1店舗で一連の動作を完成させ、次に複数店舗化する。外部予約台帳連携、Webサイト差分検出、詳細な料金計算などは、基本機能が完成してから検討する。

また、作品の企画説明では「競合がいない」「一体型だから独自」と主張しない。予約管理システム未導入の店舗にとって、初めて導入しやすく、設定・操作が簡単なサービスになっているかを実際に検証する。
